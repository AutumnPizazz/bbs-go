# 将文章并入话题的设计与实施计划

状态：实施前设计

## 0. 实施前提

当前论坛尚无需要保留的生产内容、用户互动或外部 API 使用方。因此本次改造采用一次性切换，不设计存量业务数据迁移，也不承担旧文章 URL 和旧文章 API 的兼容成本。

允许的处理方式：

- 删除旧的 `Article`、`ArticleTag` 表及对应代码。
- 删除旧的文章 API、前端路由、搜索索引和后台页面。
- 直接重建搜索索引和站点地图。
- 开发和测试数据库可以清空重建；若部署环境存在临时数据，需在发布前明确允许丢弃。

本前提只适用于当前阶段。若在正式发布前出现真实用户数据、外部客户端或已被搜索引擎收录的文章 URL，必须重新设计兼容和迁移方案。

## 1. 背景

当前项目同时提供话题和文章两套内容功能。两者都支持标题、正文、作者、浏览、评论、点赞、收藏和标签，但文章仍然是独立内容域：

- `Article` 使用独立的数据模型、标签关联表和服务。
- 文章没有 `categoryId`，不能进入节点导航和节点聚合列表。
- 文章拥有独立的 API、前端路由、搜索索引、后台权限和 SEO 入口。
- 文章额外支持摘要、封面、来源链接和文章审核配置。
- 话题已经具备节点、父子节点、推荐、置顶、问答状态、动态流和统一互动能力。

相关实现：

- [节点服务](../internal/services/category_service.go)
- [文章服务](../internal/services/article_service.go)

## 2. 目标

将文章建模为一种特殊的话题格式，使文章能够：

1. 选择普通节点并出现在节点列表中。
2. 参与父节点对子节点的主题汇总。
3. 复用话题的评论、点赞、收藏、标签、推荐、置顶和内容治理能力。
4. 进入统一的话题搜索和内容发现流程。
5. 继续保留文章特有的封面、摘要、来源链接、目录和文章化展示。
6. 从第一次写入开始就使用统一的 `Topic` 实体，不产生新的 `Article` 数据。

最终不再保留独立的文章数据域。文章列表入口 `/articles` 可以继续保留为文章格式筛选视图，但文章详情使用统一的话题详情入口 `/topic/:id`。

## 3. 非目标

本计划暂不处理以下内容：

- 已存在文章数据的迁移、ID 映射和关联实体转换。
- 旧文章 URL、旧文章 API、旧文章搜索结果的兼容。
- 文章旧表的备份、双写和兼容周期。
- 问答节点和问答状态的业务规则变更。
- 动态的图片和短内容行为。
- 节点的父子层级规则。

## 4. 推荐数据模型

### 4.1 使用 Topic 作为统一实体

建议以 `Topic` 作为文章和话题的统一存储实体，不直接把 `Article` 表改造成节点表，也不在节点上增加文章数据。

在 `Topic` 增加独立的格式字段：

```text
format: post | article
```

现有字段的默认值：

```text
type   = topic / tweet / qa
format = post
```

文章使用：

```text
type     = topic
format   = article
category = 普通节点
```

这样做的原因：

- 现有 `type` 已经用于区分帖子、动态和问答，不应继续混入展示格式概念。
- `contentType` 已经表示 Markdown、HTML 等正文编码格式，不能复用。
- 文章属于普通节点内容，不需要新增 `CategoryTypeArticle`。
- 保留 `type=topic` 可以复用普通帖子已有的节点和互动逻辑。

`format` 必须使用后端常量和统一校验，不接受任意字符串。文章格式只能与 `type=topic` 组合；`tweet` 和 `qa` 的格式固定为 `post`。

### 4.2 Topic 新增字段

建议新增以下字段：

| 字段 | 用途 | 默认值 |
| --- | --- | --- |
| `format` | 区分普通话题和文章格式 | `post` |
| `summary` | 文章摘要 | 空；列表展示时可由正文生成 |
| `cover` | 文章封面 JSON | 空 |
| `source_url` | 原文或来源地址 | 空 |
| `update_time` | 编辑时间和 SEO 修改时间 | 创建时间 |

`Topic` 已经拥有 `content`、`contentType`、统计字段、`categoryId`、推荐和置顶字段，因此不重复新增正文和互动字段。

新增字段应在 `Topic` 模型、请求 DTO、响应 DTO、搜索文档和前端类型中同时定义。所有编辑入口都必须更新 `update_time`，不能只在文章编辑时更新。

封面、摘要和来源链接使用独立字段，不放进 `extraData`，因为它们会参与详情渲染、列表展示、搜索和 SEO。

## 5. 节点和发布行为

### 5.1 节点类型

文章使用现有的 `normal` 节点。普通节点可以同时容纳普通帖子、动态和文章；问答节点继续只容纳问答。

节点兼容性校验仍然按 `Topic.Type` 执行，但文章格式必须额外要求 `Type=topic`。文章发布表单只能加载普通节点，不应让用户先选择问答节点后再由服务端失败。

### 5.2 列表和导航

- `/api/topic/topics` 默认显示该节点下的所有内容格式。
- 一级节点继续汇总自身和直接子节点的内容。
- 列表卡片根据 `format` 选择普通话题或文章卡片。
- `/articles` 使用话题接口的 `format=article` 筛选。
- `/articles/tag/:id` 使用话题标签接口的 `format=article` 筛选。
- 用户主页的文章列表使用 `userId + format=article` 查询，不再查询 `Article` 表。
- 文章是否参与推荐和置顶由运营规则决定，但实现上复用话题字段和话题后台操作。

### 5.3 发布规则

文章格式发布表单应复用话题表单的节点选择器，并使用文章编辑器：

- 必须选择有效的普通节点。
- 标题和正文必填。
- 支持 Markdown；如保留 HTML 正文，也必须在详情和搜索中正确处理两种 `contentType`。
- 支持封面、摘要和来源链接。
- 服务端拒绝投票、回复可见内容、问答状态和动态图片字段。
- 附件是否开放单独配置；默认不因为复用普通话题而开放。
- 发布时使用文章模块开关和文章邮箱验证配置。
- 文章审核配置只作用于 `format=article`，审核状态仍使用统一的 `StatusReview`、`StatusOk` 和 `StatusDeleted`。

不能只在前端隐藏文章不支持的控件，`TopicPublishService` 和 `TopicService.Edit` 必须按 `format` 做服务端校验。

## 6. API 和前端计划

### 6.1 统一接口

统一接口直接作为新接口，不保留旧文章 API：

```text
POST /api/topic/create
GET  /api/topic/edit/:id
POST /api/topic/edit/:id
GET  /api/topic/:id
GET  /api/topic/topics
GET  /api/topic/tag/topics
GET  /api/topic/user_topics
GET  /api/topic/categories
```

文章创建请求可以携带：

```json
{
  "type": 0,
  "format": "article",
  "categoryId": 1,
  "title": "文章标题",
  "summary": "文章摘要",
  "content": "文章正文",
  "contentType": "markdown",
  "cover": {"url": ""},
  "sourceUrl": "",
  "tags": []
}
```

话题列表接口增加格式筛选，并明确格式与类型的组合规则：

```text
GET /api/topic/topics?format=article&categoryId=1
GET /api/topic/tag/topics?format=article&tagId=1
GET /api/topic/user_topics?format=article&userId=1
```

### 6.2 响应结构和路由

统一话题响应增加：

```text
format
summary
cover
sourceUrl
updateTime
```

前端根据 `format` 选择展示组件：

- `post`：现有话题详情和列表卡片。
- `article`：文章详情正文、封面、目录、来源和文章列表卡片。
- `tweet`：现有动态展示。
- `qa`：现有问答详情和问答状态控件。

文章详情统一使用 `/topic/:id`，其中 `id` 使用话题现有的编码规则。前端文章列表、用户主页、搜索结果、收藏列表和消息详情链接全部生成统一话题地址。

删除旧的 `/api/article/*`、`/article/:id`、独立文章编辑页和独立文章详情页。由于没有存量数据，不实现 301、ID 映射或兼容响应。

## 7. 互动、治理和运营行为

### 7.1 统一实体标识

文章从创建开始就使用：

```text
entityType = topic
entityId   = topic.Id
```

评论、评论回复、点赞、收藏、举报、用户信息流和相关事件全部引用话题实体。新代码不再创建或消费 `entityType=article`。

文章格式复用话题的评论、点赞、收藏、推荐、置顶和删除事件。若文章评论需要单独的通知文案，只区分 `Topic.Format`，不再引入独立的文章实体类型。

### 7.2 审核和反垃圾

- `articlePending` 继续控制文章格式是否进入审核状态，或在方案冻结时统一重命名为格式无关的配置。
- `createArticleEmailVerified` 继续控制文章格式发布的邮箱要求。
- 文章格式发布也必须执行统一的违禁词、验证码和用户状态检查。
- 文章发布频率若需要独立限制，应按 `format=article` 统计；否则统一按所有 Topic 统计，并补充测试。
- 文章审核、删除、恢复和搜索可见性使用统一状态语义。

### 7.3 权限

文章格式统一使用话题资源权限和话题后台管理入口：

- 作者编辑权限沿用话题编辑规则，并额外校验格式字段。
- 后台话题管理支持按 `format` 筛选和编辑文章专属字段。
- 文章审核、删除、推荐和标签维护不再依赖独立的文章权限编码。
- 删除文章专属权限定义、权限注册、前端权限常量和旧后台页面。

如果运营确实需要单独授权文章审核，应新增“文章格式权限”，而不是继续维护一套独立实体权限。

### 7.4 用户统计、动态和任务

统一实体后，默认采用以下规则：

- `User.TopicCount` 统计所有 `Topic` 格式，包括文章。
- 文章创建进入统一的关注者信息流和话题创建事件。
- 文章使用统一的话题积分、通知和内容治理流程。
- 不再为文章保留独立的实体计数或重复奖励逻辑。

若产品需要独立展示“文章数”，应新增明确的统计字段或查询，不借用已经表示话题数量的字段。

## 8. 搜索和 SEO

### 8.1 搜索

搜索只维护话题和用户两类文档。话题文档增加：

```text
format
summary
cover
categoryId
```

文章搜索使用同一话题索引的 `format=article` 条件，不再生成独立的 `article:<id>` 索引文档。需要保证：

- 文章标题、摘要、正文和标签可搜索。
- 文章搜索可以按节点过滤。
- 话题搜索不会把文章重复返回到普通话题结果，除非产品明确要求“所有内容”模式。
- 全局搜索不会重复返回同一篇文章。
- 已删除和待审核文章不出现在公开搜索中。

由于没有存量数据，切换时可以删除并重建整个搜索索引，不需要索引迁移或旧索引清理兼容逻辑。搜索重建服务只扫描 `Topic` 和 `User`。

### 8.2 SEO 和 URL

文章格式详情仍使用统一的 `/topic/:id` URL，但根据 `format` 输出文章 SEO：

- 文章使用 `Article` 结构化数据，普通话题使用 `DiscussionForumPosting`。
- canonical、Open Graph、封面、摘要、发布时间和修改时间来自统一话题响应。
- 站点地图只生成统一话题 URL，不再生成独立文章 URL 和文章站点地图。
- 文章列表 `/articles` 作为筛选页，不为旧文章 URL 提供跳转。

当前话题和文章站点地图是分开生成的，见 [seo_sitemap_service.go](../internal/services/seo_sitemap_service.go#L164)。切换后应合并为统一的 Topic sitemap，并使用 `update_time` 计算文章格式的 `lastmod`。

## 9. 数据库结构变更和代码清理

本次不做业务数据迁移，只做一次代码和数据库结构切换：

1. 为 `Topic` 增加 `format`、`summary`、`cover`、`source_url` 和 `update_time`。
2. 为旧话题设置 `format=post`，保证字段非空和默认值明确。
3. 将文章发布、编辑、详情、列表、标签和后台查询改为 Topic 查询。
4. 将文章标签改为 `TopicTag`。
5. 将文章封面、摘要、来源链接并入 Topic 渲染和搜索流程。
6. 重建搜索索引和站点地图。
7. 删除 `Article`、`ArticleTag` 模型、仓储、服务、缓存、渲染器、请求响应类型和旧路由。
8. 删除 `t_article`、`t_article_tag` 表及文章专属权限和配置读取代码。

删除旧表属于有意的破坏性结构变更，必须在发布说明中明确。数据库迁移脚本只需要处理表结构和默认值，不需要保存 old ID、new ID 或关联实体映射。

## 10. 分阶段实施

### 阶段 0：方案冻结

- 确定 `format` 合法值和 `type` 组合规则。
- 确定文章是否参与普通节点主页、推荐、置顶和统一通知。
- 确定文章是否允许附件。
- 确定用户计数、任务奖励和关注通知口径。
- 确定统一详情 URL 为 `/topic/:id`。
- 确认当前环境允许删除旧文章表和旧文章接口。

### 阶段 1：模型和读取能力

- 为 `Topic` 增加文章格式字段和文章专属字段。
- 为旧话题设置默认 `format=post`。
- 扩展话题、节点、列表、详情和编辑接口的响应。
- 扩展话题搜索文档和 `format` 筛选。
- 增加文章格式的渲染分支。

### 阶段 2：文章写入 Topic

- 文章创建和编辑页面改用统一的文章格式表单。
- 新文章直接写入 `Topic`，选择普通节点。
- 在服务端实现文章格式的字段、模块、审核、邮箱和附件校验。
- 增加文章格式的评论、点赞、收藏、推荐、置顶和审核测试。

### 阶段 3：统一前端、后台和 SEO

- `/articles` 和文章标签页改为 Topic 格式筛选。
- 文章详情改为统一 `/topic/:id` 路由和文章化展示。
- 用户主页、收藏、消息和举报链接统一使用话题实体。
- 后台话题管理支持文章格式和文章专属字段。
- 合并搜索和站点地图实现。

### 阶段 4：删除旧实现

- 删除旧文章 API、路由、页面、服务、仓储、缓存和标签关联。
- 删除文章专属权限、配置分支和搜索文档。
- 删除 `Article`、`ArticleTag` 表。
- 清空并重建搜索索引。

## 11. 验收标准

### 节点能力

- 创建文章时可以选择普通节点。
- 节点主页能够显示文章格式内容。
- 一级节点能够汇总子节点中的文章。
- 问答节点不能接收文章格式内容。
- `/articles` 可以通过 `format=article` 独立筛选。

### 内容能力

- 文章封面、摘要、来源链接和目录正常展示。
- 评论、点赞、收藏和标签行为与统一话题一致。
- 推荐、置顶和审核行为符合阶段 0 的产品决策。
- 普通帖子、动态和问答现有行为不回归。

### 统一实体

- 文章创建后只产生 `Topic` 和 `TopicTag` 数据。
- 文章互动只使用 `entityType=topic`。
- 用户主页、收藏、消息、举报和后台管理不再依赖 `Article`。
- 旧文章 API、旧文章详情 URL 和独立文章索引不再存在。

### 搜索和 SEO

- 文章可按标题、摘要、正文、标签和节点搜索。
- 普通话题搜索和文章搜索不会重复返回文章。
- 文章详情使用 `Article` 结构化数据，普通话题使用 `DiscussionForumPosting`。
- 站点地图只包含统一话题 URL。

### 工程验证

- 增加 `format` 与 `type` 组合校验测试。
- 增加文章格式发布、编辑、节点列表、详情、搜索和互动测试。
- 增加文章格式审核、权限和不支持字段拒绝测试。
- 增加普通帖子、动态和问答回归测试。
- 增加表结构删除、搜索重建和站点地图生成验证。

## 12. 总体判断

在当前没有有价值存量数据的前提下，统一使用 `Topic` 存储文章的可行性高，且不需要设计复杂的 ID 映射、关联数据转换或旧 API 兼容层。

主要工作集中在：

- `Topic` 模型和格式校验；
- 文章字段的统一响应和文章化渲染；
- 统一搜索、SEO、后台和权限；
- 删除旧文章代码和表；
- 保证普通话题、动态和问答不回归。

推荐最终形态是：

> `Topic` 作为统一内容实体，`format=article` 保留文章的展示和业务差异，节点负责内容组织，文章旧数据域和旧兼容入口直接移除。
