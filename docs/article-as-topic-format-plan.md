# 将文章并入话题的设计与迁移计划

状态：设计阶段

## 1. 背景

当前项目同时提供话题和文章两套内容功能。两者都支持标题、正文、作者、浏览、评论、点赞、收藏和标签，但文章仍然是独立内容域：

- `Article` 使用独立的数据模型、标签关联表和服务。
- 文章没有 `categoryId`，不能进入节点导航和节点聚合列表。
- 文章拥有独立的 API、前端路由、搜索索引、后台权限和 SEO 入口。
- 文章额外支持摘要、封面、来源链接和文章审核配置。
- 话题已经具备节点、父子节点、推荐、置顶、问答状态、动态流和统一互动能力。

相关实现：

- [文章模型](../internal/models/models.go#L162)
- [话题模型](../internal/models/models.go#L231)
- [节点服务](../internal/services/category_service.go)
- [文章服务](../internal/services/article_service.go)
- [话题发布服务](../internal/services/topic_publish_service.go)

## 2. 目标

将文章建模为一种特殊的话题格式，使文章能够：

1. 选择节点并出现在节点列表中。
2. 参与父节点对子节点的主题汇总。
3. 复用话题的评论、点赞、收藏、标签、推荐、置顶和内容治理能力。
4. 进入统一的话题搜索和内容发现流程。
5. 继续保留文章特有的封面、摘要、来源链接、目录和文章化展示。
6. 保持已有文章 URL、API、搜索结果和站点地图链接可访问。

## 3. 非目标

本计划暂不改变以下能力：

- 问答节点和问答状态的业务规则。
- 动态的图片和短内容行为。
- 节点的父子层级规则。
- 标签作为跨内容类型的辅助关键词的定位。
- 旧文章链接的兼容策略。

## 4. 推荐数据模型

### 4.1 使用 Topic 作为统一实体

建议以 `Topic` 作为文章和话题的统一存储实体，不直接把 `Article` 表改造成节点表，也不在节点上增加文章数据。

建议在 `Topic` 增加独立的格式字段：

```text
format: post | article
```

现有字段的默认值：

```text
type   = topic / tweet / qa
format = post
```

文章使用：

```text
type     = topic
format   = article
category = 普通节点
```

这样做的原因：

- 现有 `type` 已经用于区分帖子、动态和问答，不应继续混入展示格式概念。
- `contentType` 已经表示 Markdown、HTML 等正文编码格式，不能复用。
- 文章属于普通节点内容，不需要新增 `CategoryTypeArticle`。
- 保留 `type=topic` 可以最大限度复用普通帖子已有的节点和互动逻辑。

如果后续格式数量长期很少，也可以采用 `TopicTypeArticle=3` 的较小改动方案。但该方案必须检查所有对 `TopicType` 的数值判断，并同步修改节点类型校验、前端表单、搜索和渲染分支，因此不作为首选方案。

### 4.2 Topic 新增字段

建议新增以下字段：

| 字段 | 用途 | 迁移策略 |
| --- | --- | --- |
| `format` | 区分普通话题和文章格式 | 旧数据默认 `post` |
| `summary` | 文章摘要 | 旧文章直接迁移；为空时由正文生成 |
| `cover` | 文章封面 | 兼容现有文章封面 JSON 格式 |
| `source_url` | 原文或来源地址 | 直接迁移 |
| `update_time` | 编辑时间和 SEO 修改时间 | 旧文章迁移原值；旧话题可初始化为创建时间 |

`Topic` 已经拥有 `content`、`contentType`、统计字段、`categoryId`、推荐和置顶字段，因此不重复新增正文和互动字段。

封面、摘要和来源链接应使用独立字段，不建议放进 `extraData`，因为它们会参与详情渲染、列表展示、搜索和 SEO。

## 5. 节点行为

### 5.1 节点类型

文章使用现有的 `normal` 节点。普通节点可以同时容纳普通帖子、动态和文章；问答节点继续只容纳问答。

现有分类类型校验位于 [constants.go](../internal/models/constants/constants.go#L181)，发布和编辑时会校验节点是否支持当前内容类型，见 [topic_publish_service.go](../internal/services/topic_publish_service.go#L227)。引入 `format` 后，文章仍使用普通话题的节点兼容性，不需要改变问答节点规则。

### 5.2 列表和导航

- `/topics/category/:id` 默认显示该节点下的所有内容格式。
- 一级节点继续汇总自身和直接子节点的内容。
- 列表卡片显示“文章”标识，并在文章格式下使用封面和摘要布局。
- `/articles` 保留为文章格式筛选列表，底层查询改为 `Topic.format = article`。
- `/articles/tag/:id` 保留为文章格式的标签筛选视图。
- 文章可以参与推荐和置顶，但是否默认允许需要在运营规则中确认。

### 5.3 发布规则

文章格式发布表单应复用话题表单的节点选择器，并使用文章编辑器：

- 必须选择有效的普通节点。
- 标题和正文必填。
- 支持 Markdown，保留现有目录生成逻辑。
- 支持封面、摘要和来源链接。
- 默认关闭投票、悬赏、隐藏内容和问答控件。
- 附件是否开放需要单独配置，不能因为复用普通话题而自动开放。

## 6. API 和前端计划

### 6.1 新的统一接口

新增或扩展话题接口，使其识别 `format`：

```text
POST /api/topic/create
GET  /api/topic/edit/:id
POST /api/topic/edit/:id
GET  /api/topic/:id
GET  /api/topic/topics
GET  /api/topic/categories
```

文章创建请求可以携带：

```json
{
  "type": 0,
  "format": "article",
  "categoryId": 1,
  "title": "文章标题",
  "summary": "文章摘要",
  "content": "文章正文",
  "contentType": "markdown",
  "cover": {},
  "sourceUrl": "",
  "tags": []
}
```

### 6.2 兼容接口和 URL

迁移期间保留旧入口：

- `/article/:oldId`：根据映射表跳转到 `/topic/:newId`，建议使用 301。
- `/api/article/:oldId`：返回兼容的文章响应，或返回带新话题地址的迁移响应。
- `/api/article/articles`：改为查询 `format=article` 的话题。
- `/api/article/tag/articles`：改为查询文章格式话题的标签关联。
- 旧文章编辑、删除和收藏接口至少保留一个兼容周期。

旧入口不能直接把旧文章 ID 当作新话题 ID，因为两个表的自增 ID 可能冲突。

### 6.3 响应结构

统一话题响应增加：

```text
format
summary
cover
sourceUrl
updateTime
```

前端根据 `format` 选择展示组件：

- `post`：现有话题详情和列表卡片。
- `article`：文章详情正文、封面、目录、来源和文章列表卡片。
- `tweet`：现有动态展示。
- `qa`：现有问答详情和问答状态控件。

## 7. 互动、治理和运营行为

### 7.1 统一实体标识

新文章话题统一使用：

```text
entityType = topic
```

这样可以复用话题评论、点赞、收藏和相关事件。旧文章数据迁移时，需要将：

```text
entityType=article, oldArticleId
```

转换为：

```text
entityType=topic, newTopicId
```

评论回复的 `entityType=comment` 不变，但根评论引用的实体 ID 需要随映射更新。

### 7.2 审核和反垃圾

文章已有独立配置和反垃圾策略，不能因为写入 `Topic` 就丢失：

- `articlePending` 继续控制文章格式是否进入审核状态。
- `createArticleEmailVerified` 继续控制文章发布的邮箱要求。
- `CheckArticle` 逻辑迁移为按 `format=article` 分支执行。
- 文章的发布频率限制应继续单独统计，或明确改为与普通话题合并统计。
- 统一使用 `StatusReview`、`StatusOk` 和 `StatusDeleted` 的状态语义。

### 7.3 权限

建议在兼容周期内保留现有文章权限代码：

- 文章格式资源管理同时允许旧的文章权限和新的话题权限。
- 后台可以在话题管理中显示文章格式记录。
- 旧的文章后台页面和权限至少保留到迁移完成。
- 迁移完成后再决定是否将文章权限合并到话题权限。

### 7.4 用户统计、动态和任务

文章并入话题后，可能影响：

- 用户发帖数和文章数的统计口径。
- 发布动态和关注者通知。
- 发布话题相关任务、积分和经验奖励。
- 个人主页中的话题列表和文章列表。

建议第一阶段保留原文章的统计和通知语义，明确迁移后的产品规则后再统一计数，避免文章迁移导致用户奖励或通知重复发放。

## 8. 搜索和 SEO

### 8.1 搜索

当前搜索将 `topic` 和 `article` 作为两个独立索引实体，见 [search/common.go](../internal/pkg/search/common.go#L18)。目标是将文章索引为话题文档，并增加：

```text
format = article
categoryId
summary
cover
```

搜索 API 可以保留旧的 `/api/search/article`，内部转换为 `format=article` 的话题搜索。统一搜索增加文章格式筛选，旧的文章搜索标签页可以作为兼容入口保留。

迁移完成后必须执行完整索引重建，并验证：

- 文章标题、摘要、正文和标签可搜索。
- 节点搜索可以过滤文章。
- 全局搜索不重复返回同一篇迁移文章。
- 已删除和待审核文章不被公开搜索返回。

### 8.2 SEO 和 URL

文章格式在 `/topic/:id` 下应使用 `Article` 结构化数据，而普通话题继续使用 `DiscussionForumPosting`。

需要处理：

- 旧文章 URL 301 到新话题 URL。
- 新页面设置正确 canonical URL。
- 站点地图不重复收录旧 URL 和新 URL。
- 旧文章站点地图保留兼容周期，然后只生成新的话题 URL。
- 文章封面、摘要、发布时间和修改时间用于 Open Graph 和结构化数据。

当前文章和话题站点地图是分开生成的，见 [seo_sitemap_service.go](../internal/services/seo_sitemap_service.go#L164)。

## 9. 数据迁移映射

建议新增一张迁移映射表，至少保存：

```text
old_article_id
new_topic_id
migrated_at
```

迁移关系：

| 旧数据 | 新数据 | 说明 |
| --- | --- | --- |
| `Article` | `Topic` | `format=article`，保留作者、正文、统计和时间 |
| `ArticleTag` | `TopicTag` | 标签 ID 可复用 |
| `Comment(entity=article)` | `Comment(entity=topic)` | 替换实体类型和新 ID |
| `Favorite(entity=article)` | `Favorite(entity=topic)` | 保留用户和创建时间 |
| `UserLike(entity=article)` | `UserLike(entity=topic)` | 保留点赞关系和统计 |
| 文章搜索索引 | 话题搜索索引 | 迁移后重建 |
| 历史消息和举报 | 兼容映射或更新实体引用 | 必须避免链接失效 |

迁移脚本必须满足幂等性：重复执行不能重复创建话题、标签、评论、收藏或点赞关系。

## 10. 分阶段实施

### 阶段 0：方案冻结

- 确定 `format` 字段及合法值。
- 确定文章是否参与普通节点主页、推荐和置顶。
- 确定文章是否允许附件。
- 确定用户计数、任务奖励和关注通知口径。
- 确定旧 URL 的跳转和兼容周期。

### 阶段 1：模型和读取能力

- 为 `Topic` 增加文章格式字段和文章专属字段。
- 为旧话题回填 `format=post`。
- 扩展节点、话题详情、列表和编辑接口的响应。
- 新增文章格式的渲染分支，但暂不迁移旧文章。

### 阶段 2：新文章写入 Topic

- 文章创建页面改用统一的文章格式表单。
- 新文章写入 `Topic`，选择普通节点。
- 保留旧文章创建接口，返回兼容提示或逐步关闭。
- 增加文章格式话题的评论、点赞、收藏和审核测试。

### 阶段 3：存量文章迁移

- 创建 ID 映射表。
- 迁移文章、标签、评论、点赞、收藏及关联实体。
- 保留旧文章记录或备份，确认迁移结果后再进入只读状态。
- 执行搜索索引重建。
- 验证旧 URL、通知、举报和收藏列表仍然可跳转。

### 阶段 4：统一前端和后台

- 节点页面显示文章格式内容。
- `/articles` 改为文章格式筛选页。
- 搜索页合并或兼容文章筛选。
- 后台话题管理支持文章格式字段和文章专属字段。
- 更新站点导航、SEO 和站点地图。

### 阶段 5：清理旧实现

- 停止写入旧 `Article` 表。
- 旧文章 API 只保留兼容读取和跳转。
- 删除重复的文章服务、仓储、标签关联和前端页面。
- 在一个完整兼容周期后再评估删除旧表和旧权限。

## 11. 验收标准

### 节点能力

- 创建文章时可以选择普通节点。
- 节点主页能够显示文章。
- 一级节点能够汇总子节点中的文章。
- 问答节点不能接收文章格式内容。
- 文章格式可以在 `/articles` 中独立筛选。

### 内容能力

- 文章封面、摘要、来源链接和目录正常展示。
- 评论、点赞、收藏和标签行为与现有文章一致。
- 推荐、置顶和审核行为符合阶段 0 的产品决策。
- 普通帖子、动态和问答现有行为不回归。

### 兼容和迁移

- 旧文章 URL 能跳转到新话题 URL。
- 旧文章 API 在兼容周期内仍可使用。
- 旧文章的评论、点赞、收藏、标签、消息和举报不丢失。
- 搜索不重复、不漏数据，并正确带出节点。
- 迁移脚本可重复执行且结果一致。

### 工程验证

- 增加分类筛选和文章格式兼容的后端单元测试。
- 增加迁移脚本的幂等性测试。
- 增加旧 URL/API 的兼容测试。
- 增加文章格式详情、节点列表、搜索和互动的前端流程测试。
- 生产迁移前完成数据库备份和可回滚演练。

## 12. 总体判断

新文章采用统一 `Topic` 实体的可行性高，真正的工作量集中在存量文章迁移、实体引用转换、旧 URL 兼容和审核/权限语义保持。

推荐最终形态是：

> `Topic` 作为统一内容实体，`format=article` 保留文章的展示和业务差异，节点负责内容组织，旧文章入口负责兼容和迁移过渡。
