# 用户注册收口与节点级内容访问控制计划

状态：待实施设计

## 0. 目标和范围

本计划处理三件相互关联的事情：

1. 新用户只能由管理员从后台手动创建。
2. 密码、短信和第三方登录不得为未知身份自动创建新用户。
3. 用户拥有明确的内容访问级别：内部员工可以访问全部内容，外部客户只能访问管理员分配的节点内容。
4. 用户不能自行修改或找回密码；外部客户附件使用独立的大小和数量限制；匿名及未授权请求不得访问内容。

本计划的“内容”包括话题、文章、问答、动态、评论、附件、搜索结果、节点导航、收藏和消息中引用的内容。用户资料、登录、密码重置和已有账号的第三方绑定属于账号能力，不直接按节点过滤。

本计划不引入逐篇内容 ACL、客户邀请链接、复杂的组织/租户模型或跨站点 SSO。节点是本阶段最细的内容授权边界。

## 1. 当前实现和主要缺口

### 1.1 注册入口

当前存在多条可能创建 `User` 的路径，不能只删除注册页面：

- `POST /api/login/signup` 调用 `UserService.SignUp` 创建密码账号。
- `POST /api/login/login_sms` 在手机号不存在时直接创建用户。
- 微信、Google、Google One Tap 和 GitHub 登录在第三方身份不存在时创建用户。
- GitHub 登录还会在邮箱匹配已有账号时自动绑定第三方身份。
- 安装流程创建第一个站长账号，这是初始化例外，不能被普通注册策略阻断。

### 1.3 现有角色权限

`Role`、`Permission`、`UserRole` 和后台权限中间件已经能控制后台操作权限。该体系目前主要回答“能否访问后台接口”，不能回答“能否读取某个节点下的内容”。

本次不把节点访问范围塞进后台权限编码，也不让多个角色的组合隐式决定内容可见性。后台操作权限和内容访问范围必须是两个独立维度。

### 1.4 内容访问链路

当前公开内容接口默认允许匿名访问，查询通常只按节点、格式和状态过滤，没有按当前用户的节点范围过滤。需要覆盖：

- 节点导航、节点树、节点详情。
- 话题/文章/问答/动态列表、详情、最近内容、用户内容和标签内容。
- 关键词搜索和搜索索引过滤。
- 评论列表、评论创建、回复、举报。
- 附件下载和内容隐藏接口。
- 点赞、收藏、关注动态、消息中引用的内容。
- 站点地图和 SEO 生成，避免受限内容从公开入口泄露。

## 2. 访问策略

### 2.1 访问级别

建议在 `User` 上增加明确的内容访问级别，使用固定值而不是依赖角色组合：

```text
all                 内部员工：可访问所有启用内容
assigned_categories 外部客户：只能访问被分配节点及其子节点内容
```

站长 `owner` 始终拥有 `all` 效果。访问级别只决定内容范围，不自动授予后台管理、审核、用户管理或角色管理权限。

建议的产品展示名称：

| 访问级别 | 业务身份 | 默认能力 |
| --- | --- | --- |
| `all` | 内部员工 | 读取全部内容；具体写入和后台能力仍由角色权限决定 |
| `assigned_categories` | 外部客户 | 读取指定节点内容；默认不允许发布新内容 |

外部客户如果未来需要发帖或评论，仍必须通过同一个访问服务校验目标节点；不能因为拥有登录态就绕过节点范围。

### 2.2 匿名用户和未授权访问

本需求明确采用严格的受限访问模式：

- 匿名用户不能读取节点、内容、搜索结果、评论、附件或站点地图。
- 未登录请求只保留安装、登录、静态资源和必要的认证基础接口；公共密码找回和重置流程也不保留。
- 未授权用户即使已经登录，也不能读取不在其节点范围内的节点、内容、搜索结果、评论、附件或站点地图。
- 列表接口过滤数据前再分页，不能先取一页结果再在内存中删除无权限项。
- 详情接口对匿名或无权访问的内容返回统一的未找到或无权结果，不能泄露标题、作者、节点名称、统计信息或附件元数据。
- 禁止通过预览、缓存、推荐、用户主页、标签、搜索索引、SEO 或其他旁路接口绕过上述限制。

### 2.3 父子节点

给外部客户分配一级节点时，默认允许该节点及全部后代节点；分配二级节点时只允许该节点及其后代。节点移动、删除或禁用后，访问范围按当前有效树重新计算。

查询范围必须使用递归后代节点，而不是只依赖当前 `GetCategoryIdsForList` 的一层展开实现。

## 3. 注册策略

### 3.1 唯一的新用户创建入口

新增统一的后台建号服务，例如 `UserService.CreateManagedUser`，只接受管理员来源请求，负责一次性完成：

- 用户名、邮箱、手机号、昵称和初始密码校验。
- 用户创建和初始状态写入。
- 角色绑定。
- 内容访问级别和节点范围绑定。
- 邮箱验证状态、操作日志和缓存失效。

用户、角色和节点范围必须在同一事务中写入。创建失败时不能留下没有角色或没有访问策略的半成品账号。

后台创建表单至少包含：

- 用户名或邮箱登录标识。
- 可选手机号。
- 昵称。
- 初始密码，或由服务端生成并只显示一次的临时密码。
- 角色。
- 内容访问级别。
- 外部客户的节点范围。
- 初始状态和邮箱是否已由管理员确认。

推荐由服务端生成临时密码并只返回一次，管理员不能再次查询明文密码；如果继续采用管理员输入密码，也必须只在创建请求中传递，数据库只保存哈希。

### 3.2 禁止公共注册和自动建号

所有非后台新用户创建路径都必须在服务端拒绝：

- `LoginSignup` 直接返回稳定的“仅允许管理员注册”错误，不依赖前端隐藏。
- `LoginLoginSms` 找不到手机号时返回同一策略错误，不创建 `User`。
- 微信、Google、Google One Tap、GitHub 登录只允许已存在 `ThirdUser` 记录的用户登录。
- 未绑定的第三方身份必须先由已有账号登录，再走显式绑定流程；绑定流程只能创建 `ThirdUser`，不能创建 `User`。
- GitHub 不再因为邮箱相同而自动绑定未知第三方身份，避免绕过管理员建号和显式绑定。
- 已有账号的密码登录、手机号登录和已绑定第三方登录继续可用；密码修改和密码重置统一由管理员执行，见 3.4 节。
- 安装流程创建第一个站长账号保留为唯一初始化例外。

服务端应在统一的用户创建策略层再次校验来源，避免未来新增登录方式时直接调用底层 `UserService.Create` 绕过规则。错误码和前端文案要明确区分“登录失败”和“禁止注册”。

### 3.3 前端注册入口

- 删除或改造 `/user/signup`，显示“请联系管理员创建账号”，不再提交公共注册请求。
- 删除登录页、导航和 OAuth 回调中指向注册页的入口。
- 不隐藏已有登录方式；已绑定的存量账号仍应能登录。
- 前端显示只是体验层，不能代替后端拒绝。

### 3.4 密码管理

用户不得自行修改密码，也不得通过公共找回流程重置密码。以下能力必须从公共 API、前端入口和服务调用链中移除或永久拒绝：

- `POST /api/user/update_password` 用户自助修改密码。
- `POST /api/login/send_reset_password_email` 公共发送密码重置邮件。
- `POST /api/login/reset_password` 公共重置密码。

管理员只能通过 `/api/admin/user/update_password` 或 `/api/admin/user/reset_password` 修改指定目标用户的密码。管理员不能读取已保存的密码；若生成临时密码，只能在成功操作时向管理员返回一次明文值，数据库只保存哈希。安装流程初始化第一个站长密码仍是例外。

管理员改密必须校验操作者对目标用户的管理权限，记录操作者、目标用户和时间，并使目标用户已有会话/token 失效。密码相关服务接口必须明确接收目标用户 ID，不能把当前登录管理员误当作修改目标。

### 3.5 无用代码清理

本次实施完成后删除不再有用的注册和自助改密代码，而不是只在前端隐藏入口：

- 删除公共注册路由、handler、请求 DTO、前端注册 action、页面、入口和对应 API 封装。
- 删除普通 `UserService.SignUp` 中仅服务公共注册的路径；后台使用独立的 `CreateManagedUser`，安装流程使用独立的初始化建号路径。
- 删除短信未知手机号自动创建分支，以及微信、Google、Google One Tap、GitHub 未知身份自动建号分支。
- 删除 GitHub 同邮箱自动绑定逻辑；保留已有账号登录后的显式绑定能力。
- 删除公共密码找回/重置 handler、邮件模板、前端表单、页面、action、API 封装和不再使用的翻译、配置字段。
- 全仓库搜索并清理删除代码的路由、类型、调用方和测试残余引用；保留已有账号登录、已绑定第三方登录和管理员改密所需代码。

## 4. 数据模型

### 4.1 用户访问级别

在 `User` 增加类似字段：

```text
content_access_mode: all | assigned_categories
```

字段必须有明确默认值和后端枚举校验，不接受任意字符串。访问级别变更需要记录操作日志并清理用户缓存、权限缓存和访问范围缓存。

### 4.2 用户节点授权表

新增 `UserCategoryAccess`，建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `user_id` | 用户 ID |
| `category_id` | 节点 ID |
| `create_time` | 创建时间 |
| `update_time` | 更新时间 |

`user_id + category_id` 建立唯一约束和索引。只允许绑定启用的节点；删除、禁用节点时不物理删除授权记录，以便恢复节点后能够审计和恢复权限。

当用户为 `all` 时忽略授权表；当用户为 `assigned_categories` 时至少需要一个有效节点才能获得内容访问。用户编辑保存时应全量替换节点集合，避免残留旧授权。

### 4.3 角色和权限边界

继续使用现有 `Role` / `Permission`：

- 角色权限控制后台页面和操作能力。
- `content_access_mode` 和 `UserCategoryAccess` 控制内容可见范围。
- `owner` 可管理全部用户和权限。
- 普通用户管理者可以创建和编辑外部客户，但不能未经专门权限把用户升级为 `all`。
- 如需让非站长管理员设置访问级别，新增独立的 `dashboard.user.access_scope` 权限；设置 `all` 可再限制为站长或单独的全局访问权限。

不能让拥有普通 `dashboard.user.update` 权限的管理员通过提交任意角色 ID 或任意字段把外部客户变成全量用户。

## 5. 后端访问控制

### 5.1 统一访问服务

新增 `ContentAccessService` 或同等职责的领域服务，提供可复用判断：

```text
CanAccessCategory(user, categoryId) bool
CanAccessTopic(user, topic) bool
GetAllowedCategoryIds(user) []int64
FilterCategoryTree(user, categories) []Category
```

内部员工和站长走全量快速路径；外部客户按授权节点递归展开；未登录用户按严格模式拒绝。不能在各个 handler 中复制角色判断。

访问服务应支持按用户缓存授权范围，并在以下事件发生时失效：

- 用户访问级别更新。
- 用户节点授权更新。
- 用户角色更新。
- 节点移动、删除、禁用或恢复。

### 5.2 读取接口

以下接口必须在查询或返回前使用访问范围：

- `topic/categories`、`category_navs`、`topic/category`。
- `topic/topics`、`topic/:id`、`topic/recent`、`topic/user_topics`、`topic/tag/topics`。
- 文章、话题、问答和动态的所有格式筛选。
- `search/topic` 及 Bleve 搜索查询。
- 评论、回复、隐藏内容和附件下载。
- 收藏、点赞、最近点赞、消息和用户内容列表中引用的 Topic。
- Sitemap 和 SEO 内容生成。

详情读取必须先校验权限，再增加浏览量和构造响应。无权内容不能通过 `recent`、标签、搜索、用户主页或推荐入口间接出现。

### 5.3 查询和搜索实现

- `TopicService` 的列表方法接收当前用户或已解析的访问范围。
- 访问范围在 SQL 查询条件中完成，保证总数、游标和分页都基于可见数据。
- 一级节点筛选时使用当前节点的全部后代节点，并与用户允许节点取交集。
- 搜索服务在构建 Bleve 查询时增加允许 `categoryId` 的 OR 条件；不能搜索完成后再过滤结果。
- 如果允许节点数量过大，增加面向用户范围的搜索过滤结构或使用数据库查询回查，但必须保证不返回越权结果。

### 5.4 写入和互动接口

外部客户是否可以发布内容、评论或互动由独立的角色/功能权限决定；拥有登录态或节点访问权本身不授予写入权限。对于被授权的外部客户写入场景：

- 创建话题/文章/问答时，提交的 `categoryId` 必须属于用户范围。
- 编辑内容时，目标原节点和新节点都必须校验。
- 评论、回复、举报、点赞、收藏和隐藏内容操作前必须确认目标 Topic 可访问。
- 附件上传、绑定和下载必须通过所属内容的访问检查，不能只校验附件 ID；附件上传还必须遵守 5.5 的外部客户独立配置。
- 管理员后台的内容操作仍由后台权限控制，但列表数据也要遵守操作员的内容范围，除非操作员拥有全量访问级别。

### 5.5 外部客户附件配置

外部客户附件限制使用独立配置，不复用内部员工的通用附件上限。默认配置为：

```text
external_customer_attachment:
  enabled: true
  max_size_mb: 20
  max_count_per_content: 5
```

其中 `max_size_mb` 是单个附件的大小上限，`max_count_per_content` 是单篇话题、文章或问答最多绑定的附件数量。该配置只限制附件能力，不替代登录、节点访问和内容写入权限判断。

实施要求：

- 上传接口在读取文件时校验单个文件大小，超过 20MB 默认值即拒绝；不能只依赖前端 `accept` 或文件选择器限制。
- 创建或编辑内容时校验绑定后的附件总数，第 6 份及以上默认拒绝；替换附件时按最终绑定集合计算，不能通过分多次请求绕过数量限制。
- 外部客户上传前必须已登录，并且对目标节点具有访问权限和相应写入/上传权限；临时附件在绑定到内容时必须再次校验。
- 附件下载、预览、缩略图和元数据接口同样执行所属内容的访问检查，不能通过附件 URL、临时 ID 或缓存绕过节点授权。
- 图片上传和普通附件上传都必须明确是否受本配置约束；若系统保留不同上传接口，后端必须分别覆盖并在设置页说明适用范围。
- 将配置接入后台设置、配置 DTO、站点配置响应和前端上传提示；管理员调整配置后，新上传和新绑定立即使用新值。
- 内部员工按现有通用附件配置或全量配置执行，不受外部客户专用上限影响；管理员仍必须遵守其自身的内容访问和操作权限。

## 6. 后台管理改造

### 6.1 用户创建

扩展 `/dashboard/users` 的 `DashboardDataPageConfig`：

- 配置 `createEndpoint: /api/admin/user/create`。
- 配置 `createPermission: dashboard.user.create`。
- 增加密码、手机号、访问级别和节点范围字段。
- 节点范围使用 `/api/admin/category/options` 的异步选项，并支持父子节点展示。
- `assigned_categories` 必须至少选择一个有效节点。
- `all` 与 `assigned_categories` 切换时清理或保留草稿节点值，但提交前由后端再次校验。

如果通用后台表单不支持“创建时显示密码、编辑时隐藏密码”或访问级别联动，新增用户专用表单组件，不要向通用表单加入难以维护的用户特例。

### 6.2 用户编辑

用户详情和编辑表单显示：

- 当前访问级别。
- 当前有效节点及其父节点。
- 角色和后台权限摘要。
- 第三方绑定状态，不显示敏感凭据。

保存时执行服务端的提权校验。修改访问级别和节点授权写入操作日志，记录操作者、目标用户、旧值、新值和时间。

### 6.3 后台内容查询

后台话题、文章、用户内容和搜索重建页面需要明确操作员范围：

- 内部员工或站长可以查看全部内容，前提是拥有对应后台权限。
- 外部客户不应拥有后台管理权限；即使误配了后台权限，也不能通过后台列表绕过节点授权。
- 节点管理者修改节点或移动节点时，系统提示受影响的用户授权范围。

## 7. 数据迁移和兼容

### 7.1 新表和默认值

通过现有 `AutoMigrate` 和版本迁移增加用户访问级别字段、`UserCategoryAccess` 模型及索引。迁移必须可重试，不删除现有用户、角色、第三方绑定和内容。

### 7.2 存量用户分类

不能在没有业务确认的情况下把所有存量用户自动升级为内部员工。推荐上线前执行分类清单：

- `owner` 固定为 `all`。
- 已确认的内部员工设置为 `all`。
- 外部客户设置为 `assigned_categories`，再导入节点授权。
- 未确认身份默认设置为 `assigned_categories` 且无授权，并在后台显示待处理状态，采用失败关闭策略。

如果业务要求上线后保持所有存量用户可见，必须在切换前明确将这些用户批量标记为 `all`，并记录批处理结果；这属于一次性授权决策，不能隐式发生。

### 7.3 搜索、缓存和 SEO

- 重建搜索索引，确认文章、话题和问答的 `categoryId` 完整。
- 清理用户、权限和内容访问缓存。
- 严格模式下不要在公开 Sitemap 中输出受限 Topic URL。
- 访问级别变更后，旧 token 不应继续携带可绕过服务端检查的权限信息；权限以服务端实时数据为准。

## 8. 分阶段实施

### 阶段 0：业务规则确认

- 匿名用户和未授权用户不得访问内容、节点、搜索、评论、附件和站点地图，该规则作为本次实施前提。
- 确认外部客户是否允许发帖/评论；若允许，确认内容类型、节点范围和附件上传权限。附件默认单个 20MB、单篇 5 份。
- 确认现有用户的内部/外部分类和上线切换时间。
- 确认谁可以授予 `all` 访问级别，以及是否需要独立后台权限。

### 阶段 1：模型和策略基础

- 增加访问级别常量、用户字段和 `UserCategoryAccess` 模型。
- 实现迁移、仓储、服务、缓存失效和访问策略单元测试。
- 实现统一 `ContentAccessService`，覆盖全量、指定节点、子节点、匿名和无授权场景。

### 阶段 2：注册入口收口

- 新增管理员建号服务和事务。
- 接入后台用户创建 API 和初始角色/节点范围写入。
- 禁止密码、短信、微信、Google、Google One Tap、GitHub 的未知身份自动建号。
- 关闭 GitHub 邮箱自动绑定，改为登录后显式绑定。
- 删除注册页面、登录入口和统一错误码对应的无用代码；保留已有账号登录入口。
- 删除用户自助改密和公共密码找回/重置流程，保留管理员指定目标用户改密。

### 阶段 3：内容读取和搜索隔离

- 在节点树、Topic 列表、详情、用户内容、标签、搜索和 Sitemap 接入范围过滤。
- 在评论、隐藏内容、附件、收藏、点赞和消息引用链路接入详情权限检查。
- 接入外部客户附件独立配置，覆盖单文件大小和单篇内容附件数量校验。
- 先过滤后分页，补充越权访问和旁路入口测试。

### 阶段 4：后台用户权限管理

- 用户后台增加创建入口、访问级别和节点范围编辑。
- 增加全量访问提权保护和操作日志。
- 后台内容查询按操作员访问范围过滤。
- 增加节点变更对授权范围的影响提示和缓存清理。

### 阶段 5：存量切换和上线验证

- 生成存量用户分类和节点授权清单。
- 在维护窗口执行分类迁移、索引重建和缓存清理。
- 使用内部员工、已授权外部客户、未授权外部客户、匿名用户和禁用节点账号完成验收。
- 监控注册拒绝、越权访问、搜索过滤和附件下载失败日志。

## 9. 验收标准

### 注册和登录

- 公共密码注册接口无法创建新用户。
- 未知手机号登录不能创建用户。
- 未绑定的微信、Google、Google One Tap 和 GitHub 身份不能创建用户。
- GitHub 同邮箱账号不能自动绑定，必须由已有账号显式绑定。
- 已有密码账号、已绑定第三方账号和已存在手机号账号仍能登录。
- 管理员可从后台创建用户，并一次性配置角色、访问级别和节点范围。
- 用户调用自助改密接口、公共密码重置邮件接口和公共重置密码接口均失败或接口已删除；只有管理员可以修改指定目标用户密码。
- 管理员改密后目标用户旧会话/token 失效，改密操作有完整日志；已保存密码不可被读取。
- 安装流程仍能创建第一个站长账号。

### 内容范围

- 内部员工可以读取所有启用节点的内容，但仍受具体后台操作权限限制。
- 外部客户只能读取分配节点及其后代节点内容。
- 外部客户不能通过一级节点、标签、搜索、最近内容、用户主页、Sitemap、附件或隐藏内容接口看到未授权内容。
- 外部客户访问未授权详情时不会得到标题、作者、节点、统计或附件元数据。
- 匿名请求访问节点、内容、搜索、评论、附件和 Sitemap 全部被拒绝。
- 已登录但未获授权的外部客户访问上述资源同样被拒绝，且不能通过标签、用户主页、最近内容、推荐、预览或缓存旁路获取信息。
- 禁用或删除节点后，该节点内容不再可见；恢复节点后授权关系可按规则恢复。
- 分页、游标、总数和搜索结果都只基于用户可见内容。
- 外部客户单个附件超过 20MB 默认被拒绝，单篇内容绑定第 6 个附件默认被拒绝；管理员可以独立调整相应配置。

### 管理和安全

- 无专门权限的管理员不能把用户升级为全量访问。
- 外部客户不能通过提交任意 `categoryId` 创建或编辑未授权节点内容。
- 访问级别、节点范围和注册操作都有操作日志。
- 用户访问策略修改后缓存立即失效，旧会话不能绕过新策略。
- 普通公开社区、站长后台和现有角色权限行为没有非预期回归。

### 工程验证

- 增加注册策略服务测试和每种自动建号路径测试。
- 增加访问服务的全量、指定节点、父子节点、匿名和无授权测试。
- 增加 Topic、搜索、评论、附件和 Sitemap 的越权测试。
- 增加自助改密、公共密码重置、管理员目标用户改密、旧 token 失效、附件大小和附件数量限制测试。
- 增加后台用户创建、角色绑定、节点范围保存和全量访问提权测试。
- 增加迁移重试、缓存失效和索引重建验证。
- 使用全仓库引用检查确认删除的注册和密码流程无残余调用。

## 10. 风险和实施原则

- 仅隐藏注册按钮不是安全措施，所有创建用户的后端路径都必须拒绝未知身份。
- 仅在 Topic 详情接口检查不够，搜索、标签、附件、评论和 Sitemap 都可能泄露内容。
- 不要把内容访问范围编码进 `User.Roles` 字符串，避免角色组合产生隐式全量权限。
- 不要在分页后过滤结果，否则会造成数量泄露、游标错误和可见内容缺失。
- 所有权限判断以后端用户和数据库策略为准，前端的 `roles`、`permissions` 和节点列表只用于界面展示。
- 上线前必须完成存量用户分类；没有分类清单就不能开启严格访问模式。
