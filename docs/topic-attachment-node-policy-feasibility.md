# 帖子附件按节点限制方案可行性分析

## 1. 结论

方案可行，整体属于中等规模改造，不需要改变附件存储模型。

当前“内部/外部”只是上传限制的选择条件，附件本身已经通过 `TopicId` 关联帖子，上传接口也已经接收 `categoryId`。因此可以将附件限制从用户维度切换为节点维度。

推荐采用：

```text
全局默认附件策略
        |
        +-- 节点覆盖策略
                |
                +-- 子节点覆盖策略
```

有效策略优先级为：

```text
子节点配置 > 父节点配置 > 全局默认配置
```

未配置节点时继承上级或全局默认策略，既可以支持按节点精细控制，也可以减少重复配置。

## 2. 当前实现

### 2.1 全局配置

帖子附件配置位于 `internal/models/dto/config_dto.go` 的 `AttachmentConfig`，当前包含：

- 是否启用附件上传；
- 允许的文件扩展名；
- 单个附件大小限制；
- 每篇帖子附件数量限制；
- `ExternalCustomerAttachment`，即按用户内容访问模式使用的另一套规则。

配置以 JSON 形式保存于系统配置表，并通过公开配置接口返回给发帖页面。

### 2.2 上传流程

帖子附件上传接口为 `POST /api/attachment/upload`，请求中已经带有 `categoryId`：

1. 校验用户是否可以向节点发帖；
2. 根据用户 `ContentAccessMode` 判断使用全局规则还是“外部客户组”规则；
3. 校验单文件大小；
4. 调用 `AttachmentService.Upload` 保存文件；
5. 附件初始使用 `TopicId=0`，等待发帖时绑定。

### 2.3 发帖和编辑流程

发帖时，`TopicPublishService` 会根据系统配置校验附件启用状态和数量，然后在事务内校验附件归属并绑定到帖子。

编辑时，`TopicService` 和 `AttachmentService.ReplaceTopicAttachments` 会再次校验附件数量、归属和绑定状态。

目前创建和编辑路径的“内部/外部”判断并不完全一致，因此改造时应统一为一个节点策略解析和校验服务。

### 2.4 节点模型

节点对应 `internal/models/models.go` 中的 `Category`，目前包含父子关系、节点类型、名称、描述、状态等字段，没有附件策略。

后台节点管理使用通用 CRUD，入口为 `web/app/routes/dashboard.categories.tsx`。增加节点附件配置需要扩展节点数据模型和表单字段，或者新增独立的节点附件配置接口。

## 3. 目标配置模型

建议保留一套全局“默认附件策略”，删除按用户区分的配置：

```text
AttachmentPolicy
  enabled       是否允许附件
  allowedTypes  允许的扩展名
  maxSizeMB     单个附件大小，0 表示不限制
  maxCount      每篇帖子附件数量，0 表示不限制
```

节点配置应支持继承。为了区分“未设置”和明确关闭，节点策略中的字段不能全部依赖 Go 或数据库零值：

- `enabled` 需要区分“未设置”和 `false`；
- 数值字段需要区分“未设置”、正数和 `0`；
- `allowedTypes` 需要区分“继承”和明确的空列表。

可以使用可选字段、JSON 配置中的字段存在性，或单独的 `inherit` 标志实现。

## 4. 存储方案

### 4.1 将策略直接放在节点表

给 `Category` 增加附件配置字段或 JSON 配置字段。

优点：

- 改动文件较少；
- 现有节点 CRUD 可以继续复用；
- 适合策略字段长期固定的情况。

缺点：

- 节点模型会混入较多业务配置；
- `allowedTypes` 等结构化字段需要额外序列化处理；
- 未来扩展用户组、审核、总容量等规则时不够灵活。

### 4.2 新增节点附件策略表

例如新增 `category_attachment_policy` 表，以 `category_id` 唯一关联节点，并保存策略字段。

优点：

- 附件规则与节点基本信息解耦；
- 更容易表达继承、覆盖和未来扩展；
- 不需要让节点模型承载复杂 JSON。

缺点：

- 需要新增模型、仓储、服务和管理接口；
- 后台节点编辑需要增加自定义配置区域；
- 查询有效策略时多一层解析。

如果本次只需要启用、类型、大小、数量四项，并且短期不会继续扩展，直接扩展节点模型即可。如果附件策略会继续演进，建议使用独立策略表。

本次实现选择直接扩展 `Category`：节点保存是否覆盖、启用状态、允许类型、单文件大小和每帖数量；未覆盖时由服务层按子节点、父节点、全局默认的顺序解析。由于项目仍处于开发阶段，后续如策略维度明显增加，再拆分为独立策略表即可。

## 5. 后端改造边界

### 5.1 统一策略解析

新增统一的有效策略解析能力，例如：

```text
GetEffectiveAttachmentPolicy(categoryId)
```

所有上传、发布和编辑路径都必须调用它，不能分别读取系统配置或自行判断用户类型。

### 5.2 上传阶段

`AttachmentService.Upload` 需要接收 `categoryId`，并在服务层完成：

- 节点是否允许上传；
- 扩展名是否允许；
- 文件大小是否超限。

仅在 Handler 层校验不够，因为其他调用方或未来新增接口可能绕过 Handler。

上传接口仍然需要先校验 `CanWriteCategory`，节点附件策略是写权限之后的附加限制，不应替代节点访问权限。

### 5.3 发帖绑定阶段

上传得到的附件在发帖前 `TopicId=0`，因此发帖时必须再次校验：

- 附件是否属于当前用户；
- 附件是否已绑定其他帖子；
- 附件数量是否满足目标节点规则；
- 每个附件的大小和类型是否仍满足目标节点规则；
- 节点是否仍允许附件上传。

数量判断应按去重后的附件 ID 计算，避免重复 ID 造成校验和实际绑定结果不一致。

### 5.4 编辑和更换节点

编辑帖子时，特别是更换 `categoryId` 时，需要按照新的目标节点重新校验现有附件。

建议不自动删除不符合规则的附件，而是拒绝本次保存并返回明确错误，避免用户无意丢失附件。

### 5.5 下载权限

附件下载仍应根据帖子本身的内容访问权限判断。节点附件限制是上传和绑定限制，不应被当成下载权限。

## 6. 前端改造

### 6.1 节点管理

节点管理表单增加附件策略配置，至少包括：

- 是否允许附件；
- 允许的文件类型；
- 单文件大小；
- 每篇帖子数量；
- 继承上级或默认配置的选项。

“外部客户组附件限制”相关字段、标签、提示语需要删除或改为节点附件策略。

### 6.2 发帖和编辑页面

发帖页面当前使用全局 `attachmentConfig` 决定是否展示附件区域，并用全局配置显示数量和大小提示。改造后应根据当前节点的有效策略：

- 决定是否显示附件控件；
- 设置文件选择器的 `accept`；
- 显示数量和大小提示；
- 在切换节点时更新策略并处理已上传附件。

前端限制只用于体验优化，服务端校验仍是最终约束。

### 6.3 配置返回方式

可以将附件策略随节点树或节点详情返回，也可以提供单独的节点策略接口。

如果策略采用继承，建议接口直接返回解析后的有效策略，同时保留节点是否覆盖的状态，减少前端重复实现继承逻辑。

## 7. 编辑器图片上传的范围

`POST /api/upload` 是编辑器内嵌图片上传，不会创建 `Attachment` 记录，也不属于帖子附件列表。

但当前接口也复用了 `ExternalCustomerAttachment` 的开关和大小限制。因此删除“内部/外部”概念时需要明确处理：

- 如果本次只改帖子附件：编辑器图片继续使用自己的全局图片上传限制，并移除外部客户判断；
- 如果内嵌图片也要按节点限制：接口必须额外接收 `categoryId` 或 `topicId`，并单独定义图片策略。

不建议直接把帖子附件的扩展名规则套用到编辑器图片上传。

## 8. 配置替换和初始化

项目仍处于开发阶段，不需要保留旧配置的读取或转换逻辑。可以直接删除：

- `ExternalCustomerAttachment` 数据结构；
- 全局配置中的“内部/外部”相关字段；
- 后台对应表单和多语言文案；
- 按 `ContentAccessMode` 选择附件规则的代码。

开发环境中的系统配置和节点数据可以直接清理或重建，不需要增加兼容迁移。新的全局配置直接定义为默认附件策略，节点配置为空时继承该策略。

默认值可以沿用当前产品预期值，例如单文件 10 MB、每帖 5 个附件；这属于新功能的初始化选择，不是旧数据兼容要求。

节点策略变更只影响之后的上传、发帖和编辑，不需要为开发阶段的历史帖子增加批量迁移逻辑。附件下载仍按帖子访问权限控制。

## 9. 风险和测试重点

需要覆盖以下场景：

- 节点关闭附件时，上传接口和发帖绑定接口都拒绝；
- 节点允许附件但限制扩展名、大小或数量时，服务端严格执行；
- 父节点和子节点的继承、覆盖关系正确；
- 上传到宽松节点后，不能绑定到严格节点而绕过限制；
- 编辑帖子更换节点时重新校验附件；
- 创建和编辑的数量校验保持一致；
- 重复附件 ID 不会绕过数量限制；
- `0` 的大小和数量限制表示不限制；
- 附件下载权限仍由帖子内容访问权限控制；
- 编辑器内嵌图片上传不受帖子附件扩展名规则错误影响；
- 没有节点配置时能够正确使用全局默认策略。

## 10. 实施判断

该需求不涉及附件存储、对象存储或下载协议重构，主要是配置模型、统一校验服务、节点管理界面和发帖页面联动。实现难点集中在“临时附件再次绑定”和“编辑时更换节点”两个边界。

推荐实施顺序：

1. 定义节点策略和继承语义；
2. 增加策略存储及有效策略解析服务；
3. 统一上传、发布、编辑校验；
4. 增加节点管理配置；
5. 修改发帖和编辑页面；
6. 删除旧的内部/外部文案和配置字段；
7. 补充绕过和边界测试。
